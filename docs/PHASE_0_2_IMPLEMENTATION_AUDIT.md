# Product Blueprint Phases 0–2 — Implementation Audit

**Audit date:** 2026-09-29  
**Audited revision:** `7337f82` (`feat: add health checks and worker observability`)  
**Scope:** Implementation and end-to-end evidence for Phases 0, 1, and 2 in [PRODUCT_BLUEPRINT.md](PRODUCT_BLUEPRINT.md). This is a codebase audit, not a production certification or legal review.  
**Application-code changes:** None. This report and the small Blueprint status corrections are documentation-only.

## Executive verdict

- **Phase 0 — Foundation: Partially implemented; exit criterion not met.** In-house registration/login, organization membership, capability checks, application-layer tenant filters for the new hiring routes, hash-chained audit events, and a small migration ledger exist. However, the legacy interview/evaluation API remains anonymous and globally scoped even for evaluations carrying `org_id` and `owner_user_id`. Resource-assignment checks and PostgreSQL RLS are absent; the latter was deliberately deferred by D-01.
- **Phase 1 — Marketplace: Core candidate/recruiter flows exist, but the phase is incomplete.** Profile and answer-vault APIs, job discovery, applications, recruiter campaigns/postings, applicant transitions, referrals, and corresponding pages are present. Resume upload/parsing, invitation acceptance, interview scheduling/calendar flows, configurable per-posting stages, and integration of the interview agents into an application stage are missing.
- **Phase 2 — Intelligence: Stage 1 exists, but is partial and has correctness defects.** Deterministic candidate/job matching is called by candidate and recruiter routes and displayed in the UI; recruiter funnel, overview, and selection-rate analytics also have routes and a page. There is no benchmark showing recommendation quality or fairness. A valid one-sided experience bound crashes matching, and a zero-selection segment is incorrectly omitted from the adverse-impact ratio.
- **End-to-end validation is API-level, not browser-level.** The HTTP tests exercise mocked agent flow and marketplace routes against isolated SQLite. The relevant Phase 0–2 suites passed **187 tests** in this audit. A prior full-suite run on the audited revision passed **202 tests** with one Starlette/httpx deprecation warning. Frontend type-check passed. There are no browser/E2E tests, no automated real-Postgres test, and no live-provider test in CI. A manual live-agent smoke test is recorded in [TESTING.md](TESTING.md), but it was not repeated during this audit.

## Evidence and method

Reviewed database DDL/migrations, auth/RBAC dependencies, candidate and recruiter routes, matching and analytics functions, frontend pages, and test coverage. Ran the relevant backend tests (`test_identity`, `test_hiring`, `test_matching`, `test_routes`, `test_database`, `test_job_worker`, `test_health`, and `test_observability`): **187 passed, 1 warning**. Rechecked TypeScript with `tsc --noEmit`: success. Reproduced the findings below using code inspection and isolated `TestClient` probes against temporary SQLite databases containing synthetic data only.

The backend test fixture intentionally uses a fresh SQLite database; it is not evidence of PostgreSQL concurrency or dialect parity. See [TESTING.md](TESTING.md#L150-L165) and [DEPLOYMENT.md](DEPLOYMENT.md#L39-L46). The application suite mocks agent calls; it validates orchestration contracts, not current live model quality.

### Confirmed Phase 0 issues

1. **Critical — legacy evaluation isolation is not enforced.** Nullable tenant/owner columns do not protect a row unless every read and write checks them. They currently do not. The legacy surface also accepts anonymous round answers/finalization, so an ID is effectively a bearer reference to read or alter interview progress. The mutating, paid `/final-decision` operation remains a `GET`. Public projections exclude `resume_text`, but candidate names, verdicts, status, and decisions remain globally accessible. See the route links in the table above; the runtime probe confirmed `200` for both anonymous detail and list.
2. **High — discoverable-profile search returns an overbroad projection.** The repository selects `cp.*`, including `resume_text`, phone, work authorization, consent and retention metadata, then joins candidate name/email. A synthetic discoverable profile's raw-resume marker and those fields were present in the authorized recruiter-search response. The opt-in flag is checked, but the API has no per-field disclosure boundary and returns more than the recruiter page renders. See [candidate_db.py](../backend/candidate_db.py#L308-L356) and [recruiter_routes.py](../backend/recruiter_routes.py#L344-L370). This is an over-disclosure risk, not a cross-tenant query leak.
3. **High — application-scoped access is not concurrency-safe by construction.** `transition_application` reads the current stage, validates in Python, then updates by ID/org without `SELECT ... FOR UPDATE` or a compare-and-swap predicate on the old stage. The suite exercises sequential transitions, not competing PostgreSQL requests. Treat race behavior as unverified until a real-Postgres concurrent test exists. See [hiring_db.py](../backend/hiring_db.py#L531-L563).
4. **Medium/high — consent metadata is auto-stamped, not explicitly obtained.** First profile creation unconditionally records consent version `v1`; the upsert request has no consent field or version supplied by the user. The current timestamp should not be represented as proof of informed consent without a deliberate consent screen and recorded acceptance. See [candidate_routes.py](../backend/candidate_routes.py#L68-L84), [candidate_db.py](../backend/candidate_db.py#L120-L127), and [hiring_models.py](../backend/hiring_models.py#L12-L31).
5. **Medium — impersonation attribution is not carried through the issued token.** The admin route creates a normal target-user token; `create_access_token` only emits subject/timing/JTI fields, and actor loading never sets `impersonated_by`. Thus downstream audit events cannot reliably distinguish the impersonating admin despite comments claiming they can. See [admin_routes.py](../backend/admin_routes.py#L102-L143), [security.py](../backend/security.py#L98-L116), and [authz.py](../backend/authz.py#L65-L115). This is adjacent platform-admin functionality, not a Phase 0–2 exit feature, but should be fixed before using impersonation operationally.

### Confirmed Phase 2 correctness defects

- **Matching crash, reproducible:** `_score_experience(5, 3, None)` raises `TypeError` at `years - hi`. A posting with a minimum experience requirement and no maximum is allowed by the posting model, and recruiter-to-candidate ranking invokes this function. This can fail a whole recommendation request. See [matching.py](../backend/matching.py#L78-L98) and [hiring_models.py](../backend/hiring_models.py#L97-L119).
- **False negative in adverse-impact ratio, reproducible:** one segment with selection rate 1.0 and another with rate 0.0 returned ratio `1.0` and `flag_adverse_impact: false`; the code filters zero rates from the numerator. A zero-selected segment should not be excluded from the lowest-rate calculation. See [hiring_db.py](../backend/hiring_db.py#L813-L883) and [test_matching.py](../backend/tests/test_matching.py#L454-L477), whose fixture does not cover a zero-rate group.

## Readiness recommendation for Phase 3

The Phase 3 prep suite itself is **not present**: no curated topic graph/problem bank, submission model, execution runner, roadmap generator, gamification records, or prep-suite UI were found. `mark_skill_verified` is a repository helper, not an end-to-end assessment path.

Before Phase 3 handles user submissions or feeds verified skills into matching:

1. Close the legacy evaluation tenant/auth gap (or explicitly isolate it as a synthetic-only demo surface).
2. Restrict recruiter search to an explicit, candidate-approved response projection; decide consent/retention and deletion behavior rather than treating an auto-stamped `v1` as consent evidence.
3. Fix and regression-test both matching defects; add a test for zero-selection segments.
4. Decide the isolated execution provider and threat model from [DECISIONS.md](DECISIONS.md#d-03-code-execution-sandbox). Never execute submitted code in the API/worker process or with production credentials.
5. Add browser journey coverage and real-Postgres concurrency tests before asserting marketplace/E2E readiness.

Low-risk work such as a curated topic DAG, problem metadata, and non-executing roadmap planning can be designed separately. Do not claim Phase 0–2 complete or launch a user-code runner based only on the current SQLite/mock suite.
